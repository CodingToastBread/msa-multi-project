# Kafka 개념 정리

## 클러스터 / Node

- **클러스터**는 여러 서버에 걸쳐 존재하는 Node 들을 묶는 논리적인 개념

- **Node** 는 카프카 프로세스 하나. 역할을 부여받아 동작한다.
    - `broker` 역할: Producer/Consumer 의 요청을 받아 메시지를 관리
    - `controller` 역할: 메타데이터 관리, 파티션 리더 지정
    - 한 노드가 둘 다 겸할 수 있다 (실습 환경). 실무에서는 보통 분리
    - 실무에서는 Node 하나당 서버 하나가 정석이지만, 정의상 필연은 아니다. Node 는 프로세스 단위지 하드웨어 단위가 아니다.

## Topic

- 하나의 논리적인 저장 주제. 말 그대로 Topic(=주제). 자체적으로 데이터를 갖지 않는다.

## Partition

- 실제 Topic 의 저장 형태이며 디렉토리+로그파일의 형태로 파일시스템에서 관리된다.
- 1..N 개로 존재할 수 있고, 토픽 생성 시 정한다. 늘릴 수는 있지만 줄일 수는 없다.
- 메시지는 파일 끝에 append 만 되고, 0부터 순번(offset)이 부여된다. offset 은 그 파티션 안에서만 유효하다.
- Partition 개수와 Node 개수는 무관하다. 파티션 10개에 노드 3대면 4/3/3 으로 나뉘고, 노드 1대면 그 한 대가 전부 맡는다.

### 리더

- 각 Partition 마다 담당 Node 가 하나씩 지정되며, 이를 **"그 파티션의 리더"** 라고 한다.
- 노드의 종류가 아니라 파티션별 역할이므로, 같은 노드가 orders-0 에서는 리더이고 orders-1 에서는 복제본일 수 있다.
- 읽기/쓰기는 해당 파티션의 리더가 처리한다.

### 복제본

- `--replication-factor` 로 정한다. 이 값은 복제본 개수가 아니라 **총 사본 수**다. 3이면 리더 1 + 팔로워 2.
- 1이면 복제본이 없다(실습 환경). 2 이상이면 다른 Node 에 같은 내용이 복제된다.
- 쓰기/읽기 분산용이 아니라 리더 장애에 대비한 것이다. 리더가 죽으면 복제본 중 하나(ISR 목록에 있는 것)가 리더가 된다.
- 실무에서는 **노드 수와 무관하게 3** 으로 둔다. 노드가 30대여도 3이다. 안전성은 3에서 충분한데 그 이상은 디스크·네트워크 비용과 쓰기 지연만 늘어난다.
- 노드가 2대뿐이면 2, 1대면 1. 노드 수를 보는 건 이 경우뿐이다.

### 분산의 두 축

| | 정하는 기준 |
|---|---|
| `--partitions` | 필요한 처리량과 Consumer 수 |
| `--replication-factor` | 3 (노드 수와 무관) |

- 읽기 분산은 복제본이 아니라 **파티션 개수**로 해결한다. 파티션이 늘면 리더가 여러 Node 에 흩어지고, Consumer 도 그만큼 병렬로 붙을 수 있다.
- 노드를 늘리는 이득은 복제가 아니라 **파티션이 흩어질 자리** 가 늘어나는 것이다.

### 순서 보장

- 순서 보장은 오직 한 Partition 안에서만 성립한다.
- 파티션이 1개면 토픽 전체 순서가 보장된다.
- 여러 개일 때 Producer 가 같은 key 로 발행하면 그 key 에 한해 순서가 보장된다. 전체 순서는 보장되지 않는다.

## Producer

- 파티션을 먼저 정하고(key 가 있으면 해시, 없으면 배치 단위 순환), 그 파티션의 리더에게 직접 보낸다.
- 최초 접속만 `bootstrap-servers` 목록에서 무작위로 고르며, 이때는 메타데이터만 받아온다.

## 메시지 보관

- 메시지는 읽어도 사라지지 않는다.
- 삭제는 보관 기간(`retention.ms`, 기본 7일) 으로 이루어지며 Consumer 의 소비 여부와 무관하다.

## KRaft

- Kafka + Raft. Raft 합의 알고리즘을 카프카에 맞게 구현한 것. Kafka 4.0 부터 ZooKeeper 는 완전히 제거되었다.
- 메타데이터를 `__cluster_metadata` 라는 **파티션 1개짜리 내부 토픽** 에 저장한다. 클러스터 상태 변경이 이 로그에 순서대로 쌓인다.
- 브로커는 이 토픽을 Consumer 처럼 **구독** 한다. 컨트롤러가 밀어주는 방식이 아니다.
    - 덕분에 재시작 시 마지막 offset 부터 이어서 읽으면 된다. (ZooKeeper 시절엔 전체를 다시 읽어야 했고 수십 초씩 걸렸다)

### 액티브 컨트롤러

- `controller` 역할 노드는 여러 대를 둘 수 있다. 실무에서는 보통 3대 또는 5대.
- 그중 실제로 일하는 건 한 대뿐이고, 이를 **액티브 컨트롤러** 라고 한다. 나머지는 핫 스탠바이로 대기하다가 액티브가 죽으면 대신 나선다.
- 액티브 컨트롤러는 결국 `__cluster_metadata` 토픽 단일 파티션의 리더다. 나머지 컨트롤러는 팔로워 복제본, 브로커는 옵저버 복제본.
    - 즉 파티션 리더와 별개 개념이 아니라, 같은 개념이 메타데이터 토픽에 적용된 것.
- 컨트롤러가 1대뿐이면(실습 환경) 그 하나가 자동으로 액티브이므로 구분할 필요가 없다.
- 선출은 과반(quorum) 투표로 이루어진다. 3대면 2대까지, 5대면 3대까지 장애를 견딘다. 홀수를 쓰는 이유.
- `KAFKA_CONTROLLER_QUORUM_VOTERS` 가 이 투표 명단이다.
    - 실습 환경: `1@kafka:9093`
    - 실무 예: `1@c1:9093,2@c2:9093,3@c3:9093`
